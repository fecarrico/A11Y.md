# Contributing to A11Y.md

This project is a **normative standard**, not an application. Contributing here means changing what a rule obliges someone to do — so the bar is not "does the code run", it is "**is the claim true, and is it in the right place**". This document tells you how to clear that bar. It is shorter than it looks.

## The three contributions worth the most

**1. A field report.** You applied the standard to a real project and something happened — it caught a barrier, it missed one, an agent misread a rule, an artifact never got generated. Open a [field report issue](https://github.com/fecarrico/A11Y.md/issues/new?template=field-report.yml). Three of this standard's releases (1.2.0, 1.3.0, 1.6.0) each began as exactly one of these. A documented failure of the standard is more valuable to us than a compliment, and it will be credited in the CHANGELOG the way [a11y-md-ai-test](https://github.com/mjepis7/a11y-md-ai-test) was.

**2. An erratum.** The standard states something and reality disagrees — an API that changed, an SC cited wrong, a technique that no longer works in current assistive technology. Open an [erratum issue](https://github.com/fecarrico/A11Y.md/issues/new?template=erratum.yml) with the primary source. This standard cites WCAG by Success Criterion number precisely so it can be proven wrong.

**3. A gap.** A component or situation the standard names but does not cover, or should name and does not. Open a [proposal](https://github.com/fecarrico/A11Y.md/issues/new?template=proposal.yml). Check the [§2.1 loading map](docs/en/A11Y.md#21-loading-triggers-lazy-loading-map) first — 29 guides exist, and the gap may be a missing *trigger* rather than a missing guide.

Built something with the standard? [Submit it to the gallery](https://github.com/fecarrico/A11Y.md/issues/new?template=gallery.yml).

## The evidence bar (read this before writing a rule)

- **Every normative claim is traceable.** A requirement either cites a WCAG 2.2 Success Criterion by number, or it is labeled a **House Rule†** — this standard's own policy, honestly marked as such. There is no third category. A MUST with no SC and no † will be asked to become one or the other.
- **Primary sources only.** A rule justified by a blog post summarizing a study will be asked for the study. We hold PRs to the same rule the standard holds agents to: *an unverified claim is fabricated evidence*.
- **Rules live where they fire.** Anything an AI must *do* belongs in the AI Behavior Contract (Section 2) with an explicit **event** trigger — never a phase trigger ("at final delivery" never arrives in continuous delivery). Guides carry depth; they never carry the sole copy of an obligation. This principle exists because [it failed once, in the field](CHANGELOG.md#120---2026-08-02) — see `guide-governance.md` §0.

## Mechanics

1. **Both languages, always.** Every change to `docs/en/` has its counterpart in `docs/pt-BR/` in the same PR. Not machine-pasted — the pt-BR edition is written, not translated word-for-word. If you cannot write the other language, say so in the PR and the maintainer will complete it before merge.
2. **Run the linter.** `python3 tools/lint-standard.py .` — it checks language parity, orphaned guides, missing §2.1 triggers, broken links, phase triggers and label drift. CI runs it on every PR; running it first saves a round trip.
3. **Update the CHANGELOG** under the version the maintainer indicates (releases are cut by the maintainer, one tag per version, no exceptions — including a version number that was skipped once to keep tags 1:1 with the CHANGELOG).
4. **New guide?** Follow the house shape: a one-line scope, a "rule everything else follows" section 0, numbered rules with the failing and correct code, a Success Criteria table, and a closing *Tip for the AI* that is a test, not a platitude. Add its row to §2.1 (a guide without a trigger is a guide that does not exist), link it from the relevant POUR section and the Reference Library, in both languages.
5. **Tools (`tools/*.py`)** are stdlib-only, dependency-free, and every check must be born from a defect that actually shipped — that is the project's rule for its own tooling. A check needs a fixture proving it catches what it claims.

## What will not be merged

- Rules that make the standard feel stricter without making an interface more usable (accessibility theater).
- Overlay widgets, automatic "remediation" layers, or anything Section 6 already prohibits — including as an "option".
- Weakening of the human-validation floor. Automated verification is welcome; it never substitutes the human checkpoints, and no contribution may let a report claim PASS without them.
- Content generated by an AI and not verified by you. Using AI to draft is fine — this project is *about* that. Signing off on unverified output is the exact failure mode the standard exists to prevent.

## Conduct

See [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). One addition specific to this project: accessibility discussions attract strong feelings for good reasons. **Attack the pattern, never the person** — a rule this repository borrows from its maintainer.
